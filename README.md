# Mini NPU Simulator — MAC 연산 기반 패턴 인식기

> **"AI 반도체의 심장인 MAC(Multiply-Accumulate) 연산을, 외부 라이브러리 없이 순수 Python으로 바닥부터 구현하다."**

NumPy 한 줄이면 끝날 연산을 **의도적으로 표준 라이브러리(`json`, `time`)만으로 직접 구현**하며,
NPU가 하드웨어 레벨에서 수행하는 연산의 본질과 그 과정에서 발생하는 **수치 오차, 데이터 무결성, 시간 복잡도** 문제를
직접 부딪히고 해결한 프로젝트입니다.

### 4-1. MAC 연산의 직접 구현 — NPU는 왜 존재하는가

#### 구현

MAC 연산은 **필터와 입력 패턴의 동일 위치 값을 곱하고, 그 결과를 하나의 누적기(Accumulator)에 계속 더하는** 연산입니다.

```python
def mac_operation(pattern, kernel):
    acc = 0.0                      # Accumulator (누적기)
    for i in range(len(pattern)):
        for j in range(len(pattern[0])):
            acc += pattern[i][j] * kernel[i][j]   # Multiply → Accumulate
    return acc
```

Cross 필터와의 MAC 점수, X 필터와의 MAC 점수를 각각 구해 **더 높은 점수의 패턴으로 분류**합니다.

#### 아키텍처 관점의 인사이트

3×3 패턴 하나를 분류하는 데 필요한 MAC 연산은 겨우 9회 × 필터 2개 = 18회입니다.
하지만 실제 CNN 모델(예: ResNet-50)은 **한 장의 이미지 추론에만 약 40억 회의 MAC 연산**을 수행합니다.

> **CPU는 이 연산을 순차적으로 처리하지만, NPU는 수천 개의 MAC 유닛을 물리적으로 병렬 배치하여
> 이 단순 반복 연산을 하드웨어 레벨에서 동시에 처리합니다.**
> "AI 반도체 = MAC 연산기의 대규모 병렬 집적체"라는 명제를,
> 직접 이중 for문을 돌려보며 그 **비효율의 크기**로 체감할 수 있었습니다.

### 4-2. 데이터 정규화 (Data Normalization) — 파편화된 라벨과의 전쟁

| 단계 | 내용 |
|---|---|
| **이슈 발생** | `data.json`의 `expected` 라벨이 `'+'`, `'cross'`, `'Cross'`, `'x'`, `'X'` 등 **작성자마다 제각각으로 파편화**되어 있어, 정답 비교 시 오판정 발생 |
| **원인 분석** | 비교 로직 곳곳에 `if label == 'cross' or label == '+' or ...` 식의 조건이 산재 → **비교 지점이 늘어날수록 누락 가능성이 기하급수적으로 증가**하는 구조적 결함 |
| **기술적 해결** | **"쓰레기는 입구에서 막는다"** 원칙 적용. 데이터 로드 직후 단 한 곳에서 내부 표준 라벨(`Cross` / `X`)로 즉시 변환하는 **정규화 계층** 도입 |
| **성과** | 이후 모든 비교 로직이 `label == 'Cross'` 단 하나로 단순화. **비교 로직의 복잡도 제거 + 데이터 무결성 확보** |

```python
LABEL_MAP = {
    '+': 'Cross', 'cross': 'Cross', 'Cross': 'Cross',
    'x': 'X',     'X': 'X',
}

def normalize_label(raw_label):
    """외부 데이터의 파편화된 라벨을 로드 즉시 내부 표준 라벨로 통일"""
    return LABEL_MAP.get(raw_label.strip(), 'UNKNOWN')
```

> **의사결정 포인트**: 비교 시점마다 변환하는 방식(Lazy)도 가능했지만,
> **입구(로드 시점)에서 단 1회 정규화(Eager)** 하는 방식을 선택했습니다.
> 시스템 내부에서는 "표준 라벨만 존재한다"는 **불변식(Invariant)** 이 보장되어,
> 이후의 모든 코드가 이 가정 위에서 안전하게 동작합니다.

### 4-3. 부동소수점 오차 제어 — Epsilon 기반 방어적 프로그래밍

| 단계 | 내용 |
|---|---|
| **이슈 발생** | 두 필터의 MAC 점수가 수학적으로 동일해야 하는 케이스에서, `score_cross == score_x` 비교가 `False`를 반환하며 **한쪽으로 잘못 판정**되는 버그 발생 |
| **원인 분석** | IEEE 754 부동소수점의 근본 한계. `0.1 + 0.2 != 0.3`처럼 **float 누적 연산은 미세한 오차(예: `5.000000000000001`)를 필연적으로 동반** → 단순 등호 비교(`A == B`)는 신뢰 불가 |
| **기술적 해결** | 허용오차 **`epsilon = 1e-9`** 를 정책으로 명문화. `abs(A - B) < epsilon`이면 "사실상 동점"으로 간주하고 **`UNDECIDED`(판정 유보)** 라는 제3의 상태로 처리 |
| **성과** | 수치 오차로 인한 **오판정 0건** 달성. "동점을 억지로 판정하지 않는다"는 정책으로 시스템의 신뢰성 확보 |

```python
EPSILON = 1e-9

def classify(score_cross, score_x):
    if abs(score_cross - score_x) < EPSILON:
        return 'UNDECIDED'   # 오차 범위 내 동점 → 판정을 유보하는 것이 정직한 결과
    return 'Cross' if score_cross > score_x else 'X'
```

> **의사결정 포인트**: 동점 시 임의로 한쪽(예: Cross)을 반환하도록 만들 수도 있었지만,
> 이는 **버그를 숨기는 행위**라고 판단했습니다.
> "시스템이 판단할 수 없는 것은 판단할 수 없다고 말해야 한다"는 원칙 하에
> `UNDECIDED` 상태를 명시적으로 설계했습니다.

### 4-4. 엣지 케이스 격리 — 하나의 불량이 전체를 무너뜨리지 않게

#### 문제 상황

| 단계 | 내용 |
|---|---|
| **이슈 발생** | `data.json` 일괄 분석 중, **스키마가 깨진 케이스**(필드 누락, 크기 불일치 등) 하나를 만나는 순간 프로그램 전체가 Crash → **뒤에 남은 정상 케이스들까지 전부 분석 불가** |
| **원인 분석** | 개별 케이스의 예외가 **격리(Isolation)되지 않고 전체 파이프라인으로 전파**되는 구조. 배치 처리 시스템에서 "하나의 불량 데이터가 전체 작업을 중단시키는" 전형적인 안티패턴 |
| **기술적 해결** | 각 케이스를 **`try-except`로 개별 보호**. 예외 발생 시 해당 케이스만 FAIL로 기록하고 **원인 메시지(스키마 불일치/크기 불일치 등)를 리포트에 명시**한 뒤, 다음 케이스로 진행 |
| **성과** | 불량 데이터가 섞여 있어도 **나머지 케이스는 100% 분석 완료**. FAIL 사유가 로그에 남아 **근본 원인 추적(Root Cause Analysis) 가능** |

#### 구현 코드

```python
for idx, case in enumerate(test_cases, start=1):
    try:
        validate_schema(case)                      # 스키마/크기 사전 검증
        result = classify(mac(case, CROSS_FILTER),
                          mac(case, X_FILTER))
        report.append((idx, 'PASS' if result == case['expected'] else 'FAIL', result))
    except SchemaError as e:
        report.append((idx, 'FAIL', f'스키마 불일치: {e}'))   # 이 케이스만 격리
    except Exception as e:
        report.append((idx, 'FAIL', f'예상치 못한 오류: {e}'))
    # → 어떤 경우에도 루프는 계속된다 (Fault Isolation)
```

> **설계 포인트**: 예외를 "숨기는" 것이 아니라 **"기록하고 격리하는"** 것이 핵심입니다.
> `except`로 잡되 FAIL 사유를 리포트에 명시함으로써, 안정성과 디버깅 가능성을 모두 확보했습니다.

#### "0 FAIL"의 진짜 의미

최종적으로 정상 데이터셋에 대해 **0 FAIL**을 달성했습니다. 이 숫자가 의미하는 바는 단순한 "테스트 통과"가 아닙니다.

> - **정규화 계층**이 파편화된 라벨(`'+'`, `'cross'`, `'x'`)을 전부 흡수했고,
> - **Epsilon 정책**이 부동소수점 오차로 인한 오판정을 전부 방어했으며,
> - **예외 격리**가 불량 케이스의 전파를 완벽히 차단했다는,
>
> 즉 **세 겹의 방어적 프로그래밍 계층이 모두 설계 의도대로 동작했음을 증명하는 지표**입니다.

이렇게 **정확성**이 확보되었으니, 다음 질문은 자연스럽게 **성능**으로 향합니다.
"이 MAC 연산, 패턴이 커지면 얼마나 느려질까?" — 4-5에서 실측으로 답합니다.

### 4-5. 시간 복잡도 O(N²) — 이론을 실측 데이터로 증명하다

#### 측정 설계

"MAC 연산은 O(N²)이다"라는 이론을 **실측으로 증명**하기 위해 다음 원칙으로 측정했습니다.

- **I/O 시간 완전 배제**: 파일 로드, 출력은 측정 구간에서 제외 — `time.perf_counter()`로 **순수 연산 구간만** 측정
- **10회 반복 평균**: 단발 측정의 노이즈(OS 스케줄링 등)를 제거하기 위해 각 크기별 10회 측정 후 평균

```python
def benchmark(pattern, kernel, repeat=10):
    total = 0.0
    for _ in range(repeat):
        start = time.perf_counter()
        mac_operation(pattern, kernel)      # 순수 연산만 측정 (I/O 배제)
        total += time.perf_counter() - start
    return (total / repeat) * 1000          # 평균 ms
```

#### 실측 결과

| 패턴 크기 (N×N) | MAC 연산 횟수 (N²) | 평균 시간 (ms, 10회) | 직전 대비 배율 |
|:---:|:---:|:---:|:---:|
| 3×3 | 9 | 0.0011 | — |
| 5×5 | 25 | 0.0030 | ≈ 2.78배 (25/9) |
| 13×13 | 169 | 0.0204 | ≈ 6.76배 (169/25) |
| 25×25 | 625 | 0.0755 | ≈ 3.70배 (625/169) |

#### 수학적 검증 — "5배 커지면 정확히 25배"

핵심 검증 포인트는 **N이 5배 커지는 구간(5×5 → 25×25)** 입니다.

> - 연산 횟수: 25회 → 625회 = **정확히 25배 (5²)**
> - 실측 시간: 0.0030ms → 0.0755ms ≈ **약 25.2배**
>
> 이론값(25배)과 실측값(≈25배)이 일치 → **MAC 연산의 시간 복잡도가 O(N²)임을 실증 데이터로 증명** ✅

이 실험을 통해 "N이 조금만 커져도 연산량은 제곱으로 폭발한다"는 사실을 수치로 확인했고,
이것이 곧 **대규모 병렬 MAC 유닛을 가진 NPU가 필요한 수학적 근거**임을 다시 한번 확인했습니다.

## 5. 보너스: 최적화 & 자동화 (핵심 차별점)

> 요구사항을 넘어, **"더 빠르게, 더 확장 가능하게"** 를 스스로에게 과제로 부여한 파트입니다.

### 5-1. 1차원 배열(Flat Array) 최적화 — 메모리 접근 패턴 개선

| 단계 | 내용 |
|---|---|
| **이슈 발생** | 2차원 리스트(`list of lists`) 순회 시, N이 커질수록 성능 저하가 이론치보다 큼 |
| **원인 분석** | Python의 2차원 리스트는 **행마다 별도의 리스트 객체가 흩어져 저장**됨 → `pattern[i][j]` 접근마다 **이중 참조(포인터 2회 추적)** 발생 + 메모리 비연속성으로 **캐시 히트율 저하**. 실제 NPU/GPU가 텐서를 1차원 연속 메모리로 다루는 이유와 정확히 같은 문제 |
| **기술적 해결** | N×N 2차원 배열을 **길이 N²의 1차원 배열로 펼침(Flatten)**. 인덱스는 `i * N + j` 공식으로 계산 — 반복문도 이중 → **단일 루프**로 축소 |
| **성과** | 인덱스 참조 1회 감소 + 연속 메모리 접근으로 **순수 연산 시간 개선**. 하드웨어 친화적 메모리 레이아웃의 효과를 직접 체감 |

```python
def mac_1d(input_1d, filter_1d):
    """2D → 1D Flat Array: 이중 루프 제거 + 연속 메모리 접근으로 캐시 효율 향상"""
    acc = 0.0
    for k in range(len(input_1d)):        # 단일 루프
        acc += input_1d[k] * filter_1d[k]
    return acc

# 2D 인덱스 (i, j) ↔ 1D 인덱스 변환: idx = i * N + j
```

> **인사이트**: 이 최적화는 단순 기교가 아닙니다.
> NumPy의 `ndarray`, GPU의 텐서 메모리, NPU의 SRAM 버퍼가 모두 **1차원 연속 메모리 위에서 동작**합니다.
> "왜 모든 고성능 연산 라이브러리는 데이터를 평평하게 펴는가?"에 대한 답을 직접 구현으로 얻었습니다.

[항목 2] 코드 구조 및 설계 주안점
Q. MAC 연산 로직의 전체 흐름은 어떻게 구현되었는가?

입력 패턴과 필터 배열의 크기(N)를 파악한 뒤, 이중 반복문을 순회하며 동일 좌표의 원소를 추출해 곱합니다(Multiply). 이 값을 누적기 변수(acc)에 지속적으로 합산(Accumulate)한 뒤 최종 점수를 반환하는 하드웨어 모사 구조입니다.

Q. 라벨 정규화(normalizer.py)를 별도로 분리한 이유와 장점은?

"쓰레기는 입구에서 막는다"는 방어적 프로그래밍 원칙의 일환입니다. 모듈을 분리하여 데이터를 로드하자마자 단 1회 정규화하면, 파이프라인 전역에서 복잡한 조건 분기 없이 단일 라벨만으로 상태를 안전하게 비교할 수 있어 결합도가 크게 낮아집니다.

Q. 시간 측정 시 I/O 배제를 위한 경계 설정은 어떻게 했는가?

benchmark.py 내에 고차함수를 정의하여, time.perf_counter()를 오직 순수 연산 함수(mac_2d 등) 호출의 바로 앞과 뒤에 밀착시켰습니다. 파일 로드나 콘솔 print 작업이 타이머 루프에 섞여 들어가는 것을 원천 차단했습니다.

[항목 3] 핵심 기술 원리 적용 (수학 & 하드웨어)
Q. MAC 점수가 높을수록 "더 유사하다"고 판단하는 원리는?

두 행렬의 픽셀 간 내적(Dot Product) 연산과 동일한 원리입니다. 필터가 1.0인 위치와 입력 패턴이 1.0인 위치가 겹칠 때만 곱셈 결과가 1이 되어 누적 점수가 상승합니다. 즉, 기하학적으로 픽셀 배치가 동일할수록 점수가 선형적으로 비례하여 증가하게 됩니다.

Q. 부동소수점 오차 발생 원인과 Epsilon 정책의 필요성은?

컴퓨터는 실수를 이진법으로 저장하므로, 무한소수를 잘라내는 과정에서 미세한 쓰레기값이 발생합니다. 이를 누적합 연산하면 0.00000001 같은 오차가 필연적으로 누적됩니다. 따라서 단순 등호(==) 비교는 치명적인 오판정을 낳으며, 오차 허용치(Epsilon) 이내는 수학적 동점으로 간주하는 정책이 필수적입니다.

Q. 패턴 크기 증가 시 측정 결과가 O(N²) 경향을 보이는 이유는?

2차원 배열을 순회하기 위해 세로(N)와 가로(N)를 도는 이중 루프 구조를 가지기 때문입니다. 실측 결과에서도 N이 5배 커졌을 때(5x5 → 25x25), 연산 횟수와 시간 모두 정확히 약 25배 증가하여 O(N²)의 시간 복잡도를 실증했습니다.

[항목 4] 시스템 확장성 및 심층 최적화 (인터뷰 대비)
Q. 새로운 라벨(예: 'O' 패턴)이 추가된다면 어떤 순서로 확장할 것인가?

구조적 결합도가 낮아 확장이 용이합니다.

normalizer.py에 'o', 'circle' 매핑을 추가합니다.

data.json과 필터 객체에 'O' 데이터를 추가합니다.

classifier.py의 판정 로직을 2개 점수 비교에서 max()를 이용한 다중 클래스 랭킹 비교 로직으로 고도화합니다.

Q. 1000x1000 패턴 처리 시 발생하는 문제와 최적화 우선순위는?

연산량 폭발보다 **'포인터 점프 병목'과 '캐시 히트율(Cache Hit Ratio) 저하'**가 더 심각한 문제를 일으킵니다. 파이썬의 2차원 리스트는 메모리에 파편화되어 있기 때문입니다. 이를 해결하기 위해 현재 보너스 과제로 적용된 1차원 평탄화(Flat Array) 메모리 레이아웃 변경을 1순위로 적용하며, 이후 다중 코어에 행(Row) 구간을 분산시키는 멀티프로세싱(Multiprocessing)을 도입해야 합니다.

Q. CPU 직렬 처리와 NPU 병렬 처리 관점에서 대규모 MAC 연산의 병목은?

CPU는 강력한 단일 코어가 방대한 MAC 연산을 순차적으로 한땀 한땀 계산하는 폰노이만 병목(Von Neumann Bottleneck)에 갇히게 됩니다. 반면 NPU는 이런 단순 곱셈-누적 유닛을 수천 개 이상 물리적으로 병렬 배치하여, 1000x1000의 행렬 연산도 단 몇 사이클(Cycle) 만에 동시에 쏟아부어 연산할 수 있습니다. 이것이 본 프로젝트가 시사하는 AI 반도체의 존재 이유입니다.
